# Gogo v1.0.0-alpha.2

Second alpha of the modular Gogo framework. This release brings the current
Admin presentation, account-ID configuration, URL-only Redis setup, Go scripts,
Async monitoring and developer documentation into the published modules.
It is not stable 1.0 or complete Django/Celery parity.

## Install

Requires Go 1.26.8 or newer. Pin the prerelease explicitly; `@latest` can select
the incompatible older stable product line.

```sh
go install github.com/Newton-School/gogo/cmd/gogo@v1.0.0-alpha.2
gogo version
gogo startproject storefront --module example.com/storefront
cd storefront
go mod tidy
go run manage.go startapp catalog
```

Configure the generated project's database settings before checks, migrations
or serving. Admin, Async and Redis remain optional, explicitly wired modules.

| Module | Git tag |
| --- | --- |
| `github.com/Newton-School/gogo` | `v1.0.0-alpha.2` |
| `github.com/Newton-School/gogo/admin` | `admin/v1.0.0-alpha.2` |
| `github.com/Newton-School/gogo/async` | `async/v1.0.0-alpha.2` |
| `github.com/Newton-School/gogo/async/redis` | `async/redis/v1.0.0-alpha.2` |
| `github.com/Newton-School/gogo/connectors/postgres` | `connectors/postgres/v1.0.0-alpha.2` |
| `github.com/Newton-School/gogo/connectors/redis` | `connectors/redis/v1.0.0-alpha.2` |

Pass the plain version to `go get`, not the directory-prefixed tag. Update all
selected Gogo modules together. For a client using all optional modules:

```sh
go get github.com/Newton-School/gogo@v1.0.0-alpha.2 \
  github.com/Newton-School/gogo/admin@v1.0.0-alpha.2 \
  github.com/Newton-School/gogo/async@v1.0.0-alpha.2 \
  github.com/Newton-School/gogo/async/redis@v1.0.0-alpha.2 \
  github.com/Newton-School/gogo/connectors/postgres@v1.0.0-alpha.2 \
  github.com/Newton-School/gogo/connectors/redis@v1.0.0-alpha.2
go mod tidy
```

## Changes since alpha.1

- Django-style Admin templates, licensed upstream CSS/JavaScript assets and
  field presentation, including date/time and autocomplete integration.
- Database-generated integer User/Group IDs by default, starting at 1, with
  explicit 64-bit integer and legacy UUID configurations.
- Redis application isolation through the database selected in
  `GOGO_REDIS_URL`; the application namespace setting and prefix are removed.
- Built-in `runscript` and `gogo.Script` for trusted, compiler-backed Go scripts
  with explicit project resources, timeouts and output bounds.
- Read-only HTML Async dashboard for tasks, workers, queues, workflows, events,
  periodic schedules and Beat instances. Authorization is required at both the
  HTTP and data-access boundaries; task payloads and raw errors are not shown.
- Redis-backed monitoring discovery, worker/Beat observations, and authenticated
  dashboard/Beat wiring in the showcase.
- Runnable PostgreSQL/Redis showcase, local Docker Compose configuration,
  field/API recipes, and focused Docusaurus documentation under Docs/Admin/Async.
- Structured contributor help and removal of the repository's AgentFlow harness.

## Upgrade precautions

### Redis keys and configuration

Remove `GOGO_REDIS_NAMESPACE`, `redis.Config.Namespace` and
`Connection.Namespace()` usage. Use a dedicated Redis database in the URL.
Internal key families remain; only the application namespace prefix is removed.

Old prefixed records are not read, renamed or deleted automatically. Stop new
submissions, drain or explicitly migrate durable delayed/periodic/workflow
state, stop old processes, and upgrade all roles together. Do not mix old and
new workers. Expect cold caches and fresh sessions, and invalidate stale session
cookies. Do not blindly strip prefixes from coordination keys.

### Existing UUID accounts

New User/Group schemas default to integer IDs. Existing UUID deployments must
select `auth.NewAccountModels(models.UUID)` consistently for account schemas,
migrations, services, Admin stores and direct ORM reads. This preserves the
original schema and migration checksum; it does not convert primary keys.

Do not delete data or reset migration history to bypass an ID-type mismatch.
Select `models.BigAuto` before the first migration when 64-bit IDs are wanted.
Application models continue to use their explicitly declared primary-key fields.

### Admin and process wiring

Review custom Admin templates/CSS against the new presentation. Dashboard routes
and Beat processes must be explicitly configured; installing a package starts
neither. The showcase dashboard requires an active staff superuser. Custom
authorization callbacks are supported; a dedicated permission-name option is
not included in this release.

`runscript` requires application source, a compatible Go compiler, cached
dependencies and executable temporary storage. It runs in a separate process,
not inside the live web server, and is not a sandbox for untrusted code. The
binary-only showcase web image intentionally cannot compile scripts.

## Remaining alpha boundaries

Task cleanup and workflow reconciliation require explicit maintenance wiring;
the showcase does not start them automatically. Task cleanup preserves active
work, pins, undelivered intents and replay protection. Workflow-record retention
cleanup remains pending. Dashboard events are bounded/lossy, and worker/Beat
observations are current snapshots rather than full history. No dashboard
retry/revoke/purge controls or complete Flower parity are claimed.

Advanced field/backend combinations, every Django Admin hook/widget, built-in
OAuth/OIDC, cloud upload adapters and environment-driven named runtime modes
remain incomplete. Delivery can repeat: business side effects need idempotency.
Production restore, failover and workload-specific load validation remain the
deploying application's responsibility.
