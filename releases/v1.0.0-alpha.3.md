# Gogo v1.0.0-alpha.3

This alpha adds independently deployable Go services in one codebase. Each
service has its own entrypoint, binary, routes, app registry and resources while
sharing domain packages, PostgreSQL data and Redis task contracts as needed.
This remains a preview, not stable 1.0 or complete Django/Celery parity.

## Install

Requires Go 1.26.8 or newer. Pin the alpha explicitly; `@latest` can select the
incompatible older stable product line.

```sh
go install github.com/Newton-School/gogo/cmd/gogo@v1.0.0-alpha.3
gogo startproject backend --module example.com/backend
cd backend
go mod tidy
go run manage.go startservice sessions
go run ./services/sessions serve --addr=127.0.0.1:8001
```

The generated service starts without database, Redis or signing credentials.
Its health endpoints are `/health/live/` and `/health/ready/`. Add only the apps,
routes, resources and optional worker commands that the service needs.

```sh
go build -trimpath -o bin/sessions ./services/sessions
./bin/sessions serve
go run ./services/sessions runserver --reload
```

## Changes since alpha.2

- `startservice NAME` creates an isolated application under `services/`, without
  modifying the main project's app registry, dependencies or environment files.
  Existing destinations, traversal and symlinked destinations are rejected.
- `Project.MainPackage` selects the package used by the `build` command and
  development reload. Reloading a service does not rebuild or launch `manage.go`.
  Empty values retain the existing root management entrypoint behavior.
- Service builds default to `bin/<service>`; `-o` remains available. Ordinary
  `go build` needs no runtime credentials; management `build` retains its
  resource-scoped configuration validation.
- New projects include a `services/` directory. There is no new public framework
  package, `cmd/` client convention or global mode environment variable.
- `examples/services` demonstrates separate API, reports and worker binaries,
  shared PostgreSQL models/migrations, bounded HTTP communication, Redis task
  publication/results, independent shutdown and service-specific dependencies.
- The example includes per-service Docker builds, local Compose configuration,
  synchronized environment templates, tests and runnable instructions.
- Documentation adds a Services page under Project with creation, configuration,
  build/reload, communication, migration and deployment examples.

## Upgrade and operational boundaries

Existing keyed `gogo.Project` declarations need no changes. Set `MainPackage`
only when using a non-default entrypoint; run development commands from the
project root. Service separation does not automatically move existing routes,
create network authentication or duplicate business logic. Each process opens
its own connections; budget pools across replicas and inject only required
credentials. Malformed declared settings and unknown `GOGO_*` values still fail
validation even when another resource is not selected.

Keep the complete shared migration graph in the root management project and run
one controlled migration job. This release introduces no framework database or
Redis key migrations relative to alpha.2. Clients upgrading from alpha.1 must
also follow the Redis-key and account-ID precautions in the alpha.2 notes.

The new example exposes public demonstration counts only, not an authenticated
business API. Its local Compose network namespace preserves the development
Redis loopback contract; it is not a production Kubernetes topology. Native
PostgreSQL/Redis integration and Compose configuration validation are distinct
from a container runtime test. Container execution was not verified for this
release because the local Docker daemon was unavailable.

All previous alpha limitations remain: no complete Django/Celery/Flower parity,
no universal production deployment certification, and no exactly-once external
effects. Use idempotent task handlers and the transactional outbox where needed.
