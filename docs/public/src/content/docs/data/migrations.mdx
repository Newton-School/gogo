---
title: Migrations
description: Generate, inspect, apply, squash, and optimize database schema changes.
---

Migrations live in each app's `migrations/` directory and describe schema
changes with explicit operations. `makemigrations` compares registered project
model metadata with the historical state produced by existing migrations; it
does not infer schema changes from filenames.

## Main workflow

```bash
go run manage.go makemigrations
go run manage.go sqlmigrate blog 0001_initial
go run manage.go migrate
go run manage.go showmigrations
```

## Maintenance commands

```bash
go run manage.go squashmigrations blog 0001 0005
go run manage.go optimizemigration blog 0005
```

## Rules

- Add migrations whenever model metadata changes database schema.
- Review generated operations before applying destructive changes.
- Keep data migrations idempotent and reversible where possible.
- Prefer additive schema changes in production systems.
- Do not edit already-applied migrations unless the project is private and the task explicitly asks for migration history cleanup.

Migration SQL rendering uses the configured dialect so teams can review the
exact SQL before rollout.

Generated Go migration files are the source of truth for operation metadata.
`sqlmigrate` and `migrate` read the file's `Operations` field; filename-based
SQL rendering is only a compatibility fallback for older placeholder files.

Applied migration history is recorded in `gogo_migrations` with dialect-aware
SQL. PostgreSQL history queries use `$1` placeholders, SQLite uses `?`, and
history upserts use `ON CONFLICT(app, name) DO UPDATE` for consistent behavior
across supported databases.

`go run manage.go migrate` takes a database-backed lock in
`gogo_migration_lock` before applying schema or history changes. A concurrent
migration run fails before operations execute; `migrate --plan` remains
read-only and does not take the lock.

`migrate --fake-initial` is for baselining an existing schema. It records an
initial migration without running SQL only when the tables, columns, primary
keys, nullability, types, defaults, collations, declared indexes, and declared
constraints match the live database where the dialect can inspect them. If the
database dialect cannot inspect table shape, fake-initial fails closed instead
of recording an unverifiable baseline.

Use `inspectdb` and `diffschema` before adopting existing tables:

```bash
go run manage.go inspectdb --table legacy_order
go run manage.go diffschema --app legacy
```

`inspectdb` emits unmanaged `models.Metadata` snippets with explicit fields,
dialect column types, defaults, indexes, and representable constraints.
`diffschema` uses the same rich table-shape comparison as fake-initial and
reports missing or mismatched declared columns, indexes, and constraints.

Unique physical indexes are represented with `IndexState.Unique` and render as
`CREATE UNIQUE INDEX` in PostgreSQL. Simple `models.Unique` constraints remain
table constraints and keep deferrable behavior; expression, partial, include, or
opclass uniqueness becomes unique index state.

Managed relation fields generate expected foreign-key constraints when their
target model metadata is registered. `diffschema` and `migrate --fake-initial`
compare those foreign keys by source column, target table, target column, and
delete action.
