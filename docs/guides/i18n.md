# Translation, timezones and humanize

`core/i18n` keeps locale and timezone decisions in the request context. `core/contrib/humanize` supplies presentation helpers without making locale a process-global setting.

## Locale selection

Start with this complete example of independent request contexts:

{{code examples/showcase/recipes/i18n/example_test.go}}

Run `go test -v ./recipes/i18n` from `examples/showcase`. The example's input locale is selected explicitly; a real HTTP app should use its configured locale middleware and supported-language allowlist.

Configure allowed languages, the default language/timezone and locale middleware. Language negotiation can use `Accept-Language`; explicit application choices must still be validated against the configured catalog. One request must not change another request's language or timezone.

## Translation catalogs

Create/load the package's explicit catalogs and use its translation/pluralization APIs. Catalog entries, contextual messages and plural rules are data, not executable template code. Missing translations and unsupported locale choices have defined fallback/error behavior in the technical catalog guide.

This package does not imply automatic extraction of every string in Go source, Django's full translation-tooling workflow or automatic propagation of locale into background tasks. Include authorized locale metadata explicitly when a job needs it.

## Dates and timezones

Keep the distinction between an instant, a calendar date and a local wall time. Forms, templates and date views use the selected timezone where appropriate. Ambiguous or nonexistent daylight-saving wall times must follow the documented resolution policy; do not silently guess an instant.

The form datetime and template date/timezone guides document accepted layouts, explicit overrides and failure cases.

## Human-readable values

{{code examples/showcase/recipes/humanize/example_test.go}}

Run `go test -v ./recipes/humanize` from the showcase directory to verify the documented formatting output.

Humanize supports localized numeric and temporal presentation and optional template filter registration. Exact integer/decimal formatting should not first convert values to imprecise `float64`.

Use the i18n recipe for isolated request contexts and the humanize recipe for formatting. Humanized output is display text, not a stable machine API or a value to write back into the database.
