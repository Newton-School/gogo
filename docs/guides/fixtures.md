# Fixtures and serialization

`core/serialization` moves explicitly selected model records into and out of fixture documents. This is data transfer, not HTTP API serialization and not a database backup format.

## Export and import

Register allowed model profiles, choose fields and scope, then use the package's export/import services. The management package provides `dumpdata` and `loaddata` factories when your project explicitly wires them. Their database and format flags must be supplied explicitly.

Export policy must filter rows and fields before bytes are written. Import policy must validate model labels, identities and fields before writes. Treat fixture files as untrusted input even if they were originally generated by your application.

## Fixture shape and commands

This JSON document describes one record of an example `notes.Note` schema with a non-auto integer key, a text title and a JSON payload:

```json
[
  {
    "version": 1,
    "model": "notes.Note",
    "pk": {"id": {"value": 42}},
    "fields": {
      "title": {"value": "Hello"},
      "payload": {"value": null}
    }
  }
]
```

`{"value": null}` is JSON null; `{"sql_null": true}` is SQL NULL. The latter requires a nullable field. JSONL uses one record object per line without the surrounding array. Your actual schema and explicit profile must match the record; this is not a fixture for the tutorial's auto-key `catalog.Product`.

After registering `DumpDataCommand` and `LoadDataCommand` with a real, authorized `serialization.New` resolver and its database resources:

```sh
go run manage.go dumpdata --database=default --format=json notes.Note > notes.json
go run manage.go loaddata --database=default --format=json --dry-run notes.Note < notes.json
go run manage.go loaddata --database=default --format=json notes.Note < notes.json
```

The alias is a configured backend name, not a connection URL. The commands are opt-in: neither the basic scaffold nor the showcase registers them automatically. See the [profile construction contract](detail-core-serialization-readme.md) and [command factory API](api-core-management.md#dumpdatacommand) when implementing the resolver. Select only the database resources it needs.

Check each exit status. Dump writes only fixture bytes; failure may leave a partial file that must not be imported. Dry-run validates and rolls back. A successful real load returns a JSON receipt and inserts the selected records; running it again is **not** an upsert.

## Features

- Deterministic JSON/JSONL fixture encoding with explicit model profiles and field handling.
- Query-backed exports with bounded work and authorization.
- Insert-only atomic import of supported scalar models with non-auto keys.
- Explicit transfer receipts and error classification at command boundaries.
- Decimal/JSON value handling without casually converting exact numbers into floating point.

## Unsupported transfers

Import profiles reject auto-generated primary keys, relations/forward references, custom codecs, arrays/extensions, generated columns and file/image fields. Export may include auto keys and a supported scalar subset. Imports require every schema field and complete explicit keys; they do not generate identities or overwrite existing rows.

Natural keys, updates/upserts, XML/custom formats, asset transfer, `flush` and automatic initial-data loading are not implemented. Use a deliberate migration/transfer program when your data needs those operations.

## Failure and retry

A partially written export is not a complete fixture. A failed import command can require examining its receipt/outcome before retrying. Do not equate a lost response with proof that no data committed. Preserve the exact artifact and operation context needed to reconcile an uncertain transfer.

Do not export password hashes, reset tokens, API credentials, private file paths or all customer rows by default. Keep backups and restore procedures separate from application fixtures.
